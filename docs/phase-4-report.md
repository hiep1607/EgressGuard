## Architecture and privacy

The sensor captures a timestamp, PID, process name, operation and normalized path in a short-lived bounded raw buffer, but never opens file content. Only files beneath normalized Windows/Program Files roots are suppressed as low-value system activity; similarly named directories in a user profile remain eligible. Once a network snapshot supplies an exact process identity, only matching events at or after that process generation start are promoted to `FileActivity`; promotion is synchronous for pre-flow correlation and duplicate-safe. The deterministic engine selects related events and persists only a salted path hash, redacted display identifier, extension, timestamps, delta, confidence and reason. No packet content, HTTPS plaintext, credential, clipboard, keystroke, cookie/token, or external telemetry is collected.

The feature is observe-only and disabled by default. File evidence never raises risk, creates a firewall rule, or activates enforcement. ETW callbacks do only cheap validation, hard-bounded short-window coalescing and bounded `TryWrite`; they never call `Process.GetProcessById` or `Process.StartTime`. The recent raw buffer has global/per-PID/dedupe hard bounds and 35-second retention; a periodic/forced bounded scan preserves out-of-order expiration semantics. The promoted handoff has matching global/exact-identity indexes with a 4,096 hard bound. The exact process-interest cache is hard-bounded with a one-minute TTL, and PID reuse is generation-safe. The Core engine keeps its insertion-order capacity semantics while a bounded timestamp index makes expiration proportional to expired candidates instead of buffer size per add. Status notifications coalesce dropped-count changes to at most about once per second and flush the exact final count on stop. Correlations are capped at 20 per flow and stored under the normal 30-day local retention. Persistence writes the complete already-bounded correlation enumeration instead of silently taking only its first 100 items. Users can remove evidence with Clear history.

## Provider, ownership, and dependency

The Windows sensor uses `Microsoft.Diagnostics.Tracing.TraceEvent` 3.2.5, owned by Microsoft, because it provides maintained kernel File I/O ETW parsing/session control without a custom unsafe P/Invoke layer. A session is named `EgressGuard.FileActivity.v2-{nonce}`. Its marker directory has protected ACLs for the controller identity, `SYSTEM`, and Administrators. The marker must exactly match version, nonce, session, PID, and start time; a live owner blocks a second controller, while a dead verified owner permits stopping only that exact session. Missing/invalid markers never authorize prefix cleanup. Local Administrators remain inside the trust boundary.

## Limitations and remaining acceptance

- Temporal correlation does not prove upload or identify transmitted contents.
- Overflow, provider variation, permission failure, late identity lookup, or very short processes can cause missed events.
- File metadata is sensitive even after redaction; evidence stays local and bounded.
- Real ETW pre-flow promotion, PID-reuse generation handling, 10-cycle lifecycle cleanup, crash/reclaim, service IPC, zero-byte loopback, raw-path redaction, stable direct `Running` sensor presentation, protected-file tooltip appearance, and UI integration at real 100%, 125% and 150% are `Verified`.
- Runtime performance remains `Verified` for baseline `9ed380f`: the final UI-online normal service CPU average was 1.100%, below the unchanged 3% budget, with bounded stress/RAM and exact cleanup. The current local technical-finding changes have deterministic bounded-work coverage but no new service/UI CPU sample, so the earlier runtime result is not relabeled as current-head evidence. The earlier 17.2% result and 3.938%-baseline table remain historical/noisy and are not reused.

## Running-to-overflow diagnosis and QA handoff

- An elevated isolated sensor reproduced the original transition without logging paths: 22,213 admitted events, zero staged backlog, a 1,098-event global raw peak, a 256-event per-PID peak, and 21,115 truthful per-PID evictions. Chrome, PowerShell and another EgressGuard process were the largest retained PID buckets. This ruled out the UI, IPC, status publication and a slow staging consumer as the original cause.
- Per-chunk reads and unrelated pre-flow mutation/open noise were entering history before a network identity existed. Unknown processes now retain only reads, identical raw reads retain the newest useful signal, and the callback coalescer prevents the same chunked operation from exhausting staging before projection. All indexes and queues retain hard bounds; dropped counters and `OverflowDegraded` remain unchanged for real loss.
- After the fix, an isolated development service stayed `Running` with zero file drops through warm-up, the synthetic loopback fixture, UI startup, evidence selection, and more than 30 seconds after the fixture read. IPC/UI returned five bounded items, including the protected `.egfixture` read at -0.770 seconds from flow first-seen. The loopback server recorded zero transmitted test bytes, and no raw path was exposed in the UI item.
- The focused DPI/tooltip acceptance is now complete: the isolated service stayed `Running` with `FileSensor=Running` and `FileDropped=0`, the protected tooltip was observed at both 100% and 150%, and the loopback test server recorded zero transmitted bytes. Production signing/Application Control remains `Blocked`, and Phase 5 has not started.
